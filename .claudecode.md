# AI Context: catalog-service

## 1. Misión del Servicio

Biblioteca central del e-commerce para productos (SKUs), descripciones, variaciones, precios base y fotos.

- **Perfil de carga:** Hiper-optimizado para lectura masiva (~90% del tráfico).
- **Persistencia:** MongoDB (Docker local).

**Responsabilidades:** ciclo de vida de productos/variantes, APIs de catálogo y eventos de dominio.  
**Fuera de alcance:** inventario operativo, precios dinámicos, auth, órdenes y pagos. La autenticación/autorización de infraestructura (OAuth2/JWT Resource Server) vive en `infrastructure` (ver `JwtAuthenticationConfig`, `SecurityConfig` y `ResourceServerJwtConfig`); el dominio no conoce nada de seguridad.

Ver también: `docs/prd.md`.

---

## 2. Reglas de Negocio y Ciclo de Vida

- **IDs:** TSID (`Long` 64 bits). Negocio: `skuBase` (familia) y `sku` (variante).
- **Estados:** `DRAFT`, `ACTIVE`, `OUT_OF_STOCK`, `ARCHIVED`.
- **Inmutabilidad:** `Product` y sus hijos son Java Records. Cambios con `toBuilder()` y copias defensivas.
- **Eventos:** los métodos de evolución acumulan eventos (`ProductCreatedEvent`, `ProductStockChangedEvent`, etc.).

---

## 3. Estándares Técnicos

### Arquitectura Hexagonal
- `domain`: modelos inmutables. **PROHIBIDO** Spring, Lombok o drivers de persistencia.
- `application`: puertos y use cases.
- `infrastructure`: adaptadores (REST, MongoDB, RabbitMQ).
- `boot`: configuración global y composition root. Conecta puertos con adaptadores.

### Principios
Aplica **SOLID**, **KISS**, **YAGNI** y **DRY**. Prioriza soluciones simples. Evita abstracciones prematuras.

### Operación
- Actuator en `/management`. Errores web deben incluir `traceId` (Micrometer).
- Comandos de build/test: ver `README.md`.
**Always**
- Testing: seguir convenciones de `TESTING_RULES.md` para crear y modificar tests.

### Boundaries

**Always**
- La composición de dependencias se hace en `boot`.
- Respeta capas hexagonales, inmutabilidad del dominio y acumulación de eventos.

**Ask first**
- Cambios de schema MongoDB, contratos públicos (API/eventos) o nuevas dependencias relevantes.

**Never**
- Lógica de negocio en `boot`.
- Dependencias desde `domain`/`application` hacia `boot`.
- Spring/Lombok/drivers en `domain`.
- Exponer modelos de dominio en controllers.
- Romper la inmutabilidad de `Product`.

## 4. Servidores MCP

Úsalos de forma especializada, mínima y just-in-time.

| Herramienta | Usar cuando | No usar cuando |
|-------------|-------------|----------------|
| **Engram** | Decisiones previas, arquitectura, preferencias, checkpoints | Cambios triviales o info ya en contexto |
| **Context7** | Docs/sintaxis de librerías o SDKs externos | Código interno |
| **Codegraph** | Firmas, call chains e impacto | Lectura de un solo archivo pequeño |

**Always**
- Herramienta más específica primero.
- Codegraph antes de editar en tareas no triviales.
- Context7 antes de usar librerías externas.
- `engram_remember` tras decisiones importantes; `engram_checkpoint` al cerrar hitos/sesión.

**Never**
- Context7 para código interno.
- Codegraph para un archivo pequeño.
- Engram en cambios triviales.
- Llamar MCPs “por defecto”.
- Ignorar fallos de MCP: indícalo y continúa.

---

## 5. Secuencia Obligatoria de Ejecución

Aplica solo a tareas **no triviales** (Feature, Bug complejo, Refactor, arquitectura).  
En cambios triviales (typos, renombres, logs) actúa directo.

**Si dudas, trátala como no trivial.**

Orden cuando apliquen varias reglas:  
`engram_recall` → Context7 → Codegraph → `engram_remember` → `engram_checkpoint`.

**Always**
- Diseño/arquitectura → `engram_recall`.
- Edición no trivial → Codegraph (sin lecturas masivas).
- Librerías externas → Context7.
- Tras endpoints/contratos/features/arquitectura, bugs de raíz, configs/migraciones o preferencias del usuario → `engram_remember` inmediato.
- Fin de sesión o hito → `engram_checkpoint`.

**Ask first**
- Tareas ambiguas de diseño.
- Duda sobre versión/best practice externa.
- Impacto en contratos públicos, eventos o schema.

**Never**
- Aplicar la secuencia en cambios triviales.
- Editar tareas no triviales sin `engram_recall` + Codegraph.
- Lecturas masivas si Codegraph basta.
- Esperar confirmación para `engram_remember` en casos Always.
- Omitir `engram_checkpoint` al cerrar trabajo relevante.
